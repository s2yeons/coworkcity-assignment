# 코워크시티 홈페이지 개선 과제 — 내 사업에 맞는 비상주사무실 찾기

> 실행 방법은 [README](../README.md)를 참고해주세요. 이 문서는 **무엇을, 왜, 어떻게** 바꿨는지에 대한 설명입니다.

## 1. 문제: 누가, 어떤 상황에서, 어떤 불편을 겪는가

코워크시티를 처음 이용하는 사용자의 입장에서 여러 페이지를 직접 탐색해보면서, **자신의 사업에 적합한 비상주사무실을 찾기 위해 사용자가 직접 여러 정보를 조합해야 한다는 점**에 주목했습니다.

코워크시티는 지점마다 지역, 사업자 유형, 과밀억제지역 여부, 인허가 업종 주소지 지원 여부, 등록 가능한 업종 등의 조건이 다르기 때문에 단순히 지역이나 가격만으로 지점을 선택하기 어렵습니다. 실제로 지점 목록에서는 다양한 필터를 제공하고 있고, 업종별 등록 가능 여부에 대한 정보도 별도의 업종 가이드에서 제공하고 있습니다.

하지만 사용자가 자신의 사업을 시작하려는 상황에서는 **"내가 하려는 사업으로 어느 지점을 이용할 수 있는가?"를 판단하기 위해 업종 정보와 지점 정보를 직접 오가며 확인해야 합니다.**

### 현재 사이트에서 확인한 정보 구조

| 페이지 | 확인한 내용 |
|---|---|
| 지점 목록 `/offices` | 지역, 우수관리지점, 결제 주기, 사업자 유형(개인/법인), 과밀 여부(과밀/비과밀), 업종(최대 3개 선택), 건축물 용도, 인허가 업종 주소지 지원(가능/불가능), 최저가/한정수량 등 **9종의 필터가 나열**되어 있음 |
| 업종 안내 `/industries` | 60여 개 업종이 **신청 사례 있음 / OEM 계약 필요 / 인허가 요건 확인 / 신청 불가** 4단계로 분류되어 있고, 업종별 참고사항(예: 위탁 제조 계약서 필요)이 있음 |
| 업종 가이드 `/guide/industries` | 등록 가능·인허가 필요·등록 불가 업종을 목록으로 안내 |
| 지점 상세 `/offices/180` | 기본 정보로 과밀/비과밀, 건축물 용도, 결제 주기, 사업자 유형, 계약 불가 업종, 인허가 업종 주소지 지원 여부, 실태조사 지원 여부를 표시. 가격은 월 결제와 연 결제가 함께 표기됨 |

즉, 사용자가 답을 얻으려면 다음을 스스로 이어 붙여야 합니다.

```text
내가 하려는 사업  →  어떤 업종인가  →  그 업종은 비상주 등록이 되는가 (업종 안내 페이지)
  →  지점 목록으로 이동  →  지역·사업자 유형·업종·과밀·인허가 필터를 하나씩 조작
  →  지점 상세에 들어가 조건을 다시 확인
```

### 같은 문제의 다른 얼굴: 이미 사업자가 있는 사람

처음 창업하는 사람만 겪는 문제가 아닙니다. 코워크시티 계약 화면에는 사업자등록번호, 대표자, 주소, 업종 입력란이 있고(페이지 데이터에서 확인), 기존 사업자가 주소를 이전하려면 **사업자등록증에 이미 적혀 있는 정보를 손으로 다시 입력**한 뒤 위와 같은 조건 확인을 거쳐야 합니다. 즉 "내 조건을 시스템에 알려주는 비용"이 두 사용자 모두에게 있습니다.

## 2. 선택 이유: 왜 이 문제를 골랐는가

탐색하면서 눈에 띈 다른 지점들(예: 지점 목록과 상세에서 가격 단위가 월/연으로 섞여 있어 비교가 어려운 점, 필터 항목이 많아 한 화면에 나열된 점)도 있었지만, 다음 이유로 이 문제에 집중했습니다.

1. **서비스의 핵심 목적과 직결됩니다.** 코워크시티의 핵심 사용 목적은 사업자등록을 위한 주소지를 찾는 것입니다. 단순히 많은 지점을 보여주는 것보다 **사용자의 사업 조건에 맞는 지점을 빠르게 좁혀주는 경험이 더 중요하다고 판단했습니다.**
2. **정보는 이미 다 있는데 연결만 안 되어 있는 문제입니다.** 업종 등록 가능 여부, 지점별 조건, 필터가 모두 존재합니다. 새 정보를 만드는 것이 아니라 흩어진 정보를 사용자의 질문 순서대로 다시 묶는 것이라, 개선 효과 대비 위험이 낮습니다.
3. **UI만 바꿔서는 해결되지 않습니다.** "내 업종으로 등록 가능한 지점"을 보여주려면 업종과 지점의 관계를 데이터로 갖고 서버에서 조회해야 합니다. 프론트와 백엔드가 모두 필요한 과제 범위에 맞는 문제입니다.
4. **처음 방문한 사용자에게 가장 먼저 부딪히는 벽입니다.** 기존 이용자는 자기 조건을 이미 알지만, 사업을 막 시작하는 사용자는 "내 업종이 뭔지"부터 막힙니다. 이 사용자층이 신규 계약으로 이어질 가능성이 가장 큽니다.

## 3. 해결 방식: 무엇을, 왜 바꿨는가

사용자가 자신의 업종, 사업자 유형, 희망 지역 등의 조건을 입력하면 해당 조건에 맞는 지점을 찾아주고, **왜 해당 지점을 추천하는지까지 함께 보여주는 기능**을 구현했습니다.

```text
내 사업 조건 입력 (검색 1번 + 선택 3번, 추가 조건은 선택 사항)
  →  서버가 DB에서 조건에 맞는 지점 조회
  →  조건에 맞는 지점 + 추천 이유 확인
```

### 3-1. 사용자 흐름 (`/offices/recommend`)

| 단계 | 화면 | 이렇게 만든 이유 |
|---|---|---|
| 1. 업종 | "어떤 사업을 하고 계신가요?" 사업 내용을 검색하면 관련 업종과 **등록 가능 여부(4단계 상태)**를 함께 표시 | 사용자는 업종 분류명이 아니라 "온라인 쇼핑몰", "앱 개발" 같은 사업 내용으로 생각하므로 키워드 검색으로 업종을 찾게 함. 신청 불가 업종은 이 단계에서 바로 안내하고 진행을 막음 |
| 2. 사업자 유형 | 개인 / 법인 | 지점마다 지원 유형이 다르고, 법인은 과밀 여부에 따라 등록세가 달라지므로 필수 조건으로 둠 |
| 3. 지역 | 지역 버튼마다 **앞 조건을 반영한 지점 수**를 미리 표시 | 결과가 0개인 지역을 고르는 헛걸음을 줄임 |
| 4. 추가 조건 | 비과밀 / 인허가 업종 주소지 지원 / 가격(월환산) | 선택 사항. **인허가 요건 업종을 골랐다면 인허가 지원 조건이 자동 적용**되고 그 이유를 안내 |
| 5. 결과 | "내 조건에 맞는 지점 N개", 카드마다 추천 순위·가격·**추천 이유**·미충족 조건 | 사용자가 "왜 이 지점인지"를 카드만 보고 이해할 수 있게 함 |

한 번에 모든 필터를 보여주지 않고 단계별로 묻는 이유는, 기존 화면의 문제가 "필터가 부족해서"가 아니라 "무엇을 어떤 순서로 골라야 하는지 모르는 것"이기 때문입니다.

### 3-2. 추천 방식: 설명 가능한 규칙 기반

AI 추천처럼 보이게 만들지 않았습니다. 사용자가 결과를 신뢰하려면 이유가 단순해야 합니다.

- **필수 조건** (하나라도 어긋나면 제외): 지역 일치, 사업자 유형 지원, 해당 업종으로 사업자등록 가능. 인허가 요건 업종이면 인허가 업종 주소지를 지원하는 지점만.
- **선택 조건** (선택한 것만 점수 반영, 우선순위에만 영향): 비과밀 +2, 인허가 업종 주소지 지원 +2, 가격 조건 충족 +1
- 정렬: 점수 → 월환산 가격 → 이름
- 응답에 `matchReasons`(충족한 조건)와 `unmetConditions`(미충족 조건)를 함께 담아 카드에 그대로 표시
- 결과가 0개면 "지역을 전체로 바꾸면 14개", "법인사업자로 바꾸면 1개"처럼 **조건을 하나 완화했을 때의 개수를 서버가 계산해 제안**

선택 조건을 필터가 아니라 우선순위로 둔 이유는, "비과밀"을 체크한 사용자에게 과밀 지점을 아예 숨기면 선택지가 급격히 줄고, 반대로 섞어서 보여주되 이유를 표시하면 사용자가 trade-off를 스스로 판단할 수 있기 때문입니다.

### 3-3. 가격 비교 기준

현재 사이트는 월 결제 금액과 연 결제 금액이 함께 표기됩니다. 이 기능에서는 **연 결제 금액을 12로 나눈 월환산 금액**을 비교 기준으로 정하고, 카드에도 "240,000원 / 1년 · 월 20,000원 환산"처럼 원래 표기와 환산값을 같이 보여줍니다.

### 3-4. 기존 사업자를 위한 두 번째 진입점: 사업자등록증으로 시작하기 (`/offices/recommend/registration`)

조건을 하나씩 고르는 대신 **사업자등록증 이미지를 올리면** 서버가 OCR로 읽어 아래를 자동으로 채우고, 같은 추천 결과 화면으로 보냅니다.

| 등록증에서 읽는 것 | 추천 조건으로 변환 |
|---|---|
| 제목의 "(일반과세자)/(간이과세자)" 또는 "(법인사업자)"·법인등록번호 | 사업자 유형 |
| 사업장 소재지의 시·도 | 지역 (추천 DB에 지점이 없는 지역이면 경고) |
| 업태 · 종목 | 업종 후보 3개 (키워드·업종명 매칭, OCR 오타는 바이그램 유사도로 흡수) |
| 사업자등록번호 | (1) 국세청 검증 자리 규칙으로 오독 감지 → (2) 국세청 진위확인·상태조회 API로 실제 존재·일치 여부 확인 |

- OCR 엔진은 tesseract.js(한국어+영어)이고 학습 데이터를 레포에 포함해 API 키나 네트워크 없이 동작합니다.
- **사업자등록번호 검증은 두 단계**입니다. 첫째, 국세청 체크섬 규칙(앞 9자리 가중치 1,3,7,1,3,7,1,3,5)으로 형식을 검사해 OCR 오독을 걸러냅니다. 이것만으로는 그 사업자가 실제로 있는지 알 수 없으므로 둘째, 공공데이터포털의 **국세청 사업자등록정보 진위확인·상태조회 API**를 호출합니다. 읽은 번호·개업일·대표자명이 국세청 기록과 일치하는지(진위확인), 계속사업자/휴업/폐업 여부와 과세 유형(상태조회)을 받아 화면에 표시하고, 불일치나 폐업이면 경고합니다. 국세청에는 이미지가 아니라 세 값만 전송됩니다. API 키(`NTS_API_KEY`, 무료 발급)가 없으면 이 단계는 "미확인"으로 표시되고 나머지 기능은 그대로 동작합니다.
- 읽은 결과는 **확인·수정 화면**을 거칩니다. OCR은 한 번에 정확하지 않을 수 있으므로 등록번호·상호·대표자·개업일·주소·업태·종목을 **모두 입력창으로** 보여주고, 고친 뒤 "수정한 정보로 다시 확인"을 누르면 이미지 없이 텍스트만 서버로 보내 국세청 확인과 업종 매칭을 다시 수행합니다(`POST /api/business-registration/verify`). 국세청 진위확인이 번호·개업일·대표자명 세 값으로 이뤄지므로 이 중 하나만 오독돼도 사용자가 즉시 바로잡을 수 있어야 하기 때문입니다. 등록번호 입력은 O/I를 숫자로 보정하고 000-00-00000 형태로 자동 정리합니다. 유형·지역·업종도 같은 화면에서 고칠 수 있고, 다 정한 뒤 "이 조건으로 지점 찾기"를 누릅니다.
- 이미지는 메모리에서만 처리하고 저장하지 않습니다. 등록증에는 개인정보가 있기 때문입니다.
- 등록증이 없는 사용자(그리고 채점자)를 위해 가상 정보로 만든 샘플 등록증 3장(개인·서울·전자상거래 / 법인·경기·소프트웨어 / 개인·부산·디자인 촬영본)을 화면에서 바로 체험할 수 있습니다. 샘플의 사업자등록번호는 검증 자리 규칙은 통과하지만 **국세청에 등록되지 않은 번호**를 골랐습니다(실제 키로 상태조회해 확인). 우연히 실존 사업자의 번호와 겹치면 가상 등록증 아래에 실제 사업자의 상태가 표시되는 문제가 있기 때문입니다.

### 3-3-1. 지도: 결과가 "어디"인지 바로 보이게

지역만 고른 사용자는 지점이 실제로 어디쯤인지 감이 없습니다. 실제 코워크시티 지점 목록도 지도 중심이므로, 추천 결과 옆(모바일은 위)에 **카카오맵을 두고 추천 순위가 적힌 마커**를 표시합니다. 마커를 누르면 해당 카드로 스크롤·강조되고, 카드에 마우스를 올리면 마커가 커집니다. 지점 상세에도 위치 지도를 넣었습니다. SDK 로드에 실패하거나 좌표가 없으면 안내만 보여주고 목록은 그대로 동작합니다. 좌표는 `Office.lat/lng` 컬럼으로 추가했고(마이그레이션), 샘플 지점 좌표는 해당 구·동 중심의 근사값입니다.

### 3-4-1. 사업자등록번호 검증: 지금 할 수 있는 것과 실제 서비스에서 하는 방법

**이 과제에서 구현·검증한 범위**

- 형식 검증: 국세청 체크섬(가중치 1,3,7,1,3,7,1,3,5)으로 OCR 오독을 감지. 단위 테스트로 검증.
- 국세청 진위확인·상태조회 API 연동: 공공데이터포털에서 발급받은 실제 인증키로 호출해 확인했습니다. 가상 샘플 등록증의 번호는 "국세청에 등록되지 않은 사업자등록번호"로, 진위확인은 `valid: "02"`(확인 불가)로 응답했고, 실재하는 공개 법인 번호(기업 웹사이트 하단에 공시된 사업자등록번호)는 "계속사업자 · 부가가치세 일반과세자"로 응답했습니다. 응답 필드는 구현과 일치했습니다. mock 응답 기반 단위 테스트 8개도 통과합니다.

**실제 서비스에서의 사업자등록번호 검증 (이 프로젝트에 구현되어 있고, 키만 있으면 동작)**

1. 공공데이터포털(data.go.kr)에서 "국세청_사업자등록정보 진위확인 및 상태조회 서비스"를 활용신청해 인증키를 받습니다(무료, 개발 계정 하루 100만 건, 30분 주기로 국세청 기록과 동기화).
2. OCR로 읽은 **등록번호·개업일자·대표자명**을 `POST /validate`에 보내 국세청 기록과 일치하는지(`valid` 01/02) 확인합니다. 이미지 자체는 보내지 않습니다. 세 값 중 하나라도 못 읽었으면 `POST /status`로 상태(계속사업자 01 / 휴업 02 / 폐업 03)와 과세 유형만 조회합니다.
3. 결과에 따라 흐름을 나눕니다. 일치 + 계속사업자면 자동 채움을 신뢰하고 진행, 불일치면 "번호·개업일·대표자를 확인해 주세요"로 수정 유도, 폐업이면 주소 이전 대신 신규 등록 안내로 분기.
4. 운영 고려: 같은 번호의 반복 조회는 짧게 캐시(예: 10분)해 할당량을 아끼고, API 장애 시에는 형식 검증만으로 진행하되 "국세청 확인 안 됨"을 표시합니다(현재 코드가 이렇게 동작). 신규 사업자는 국세청 반영에 1~2일 걸릴 수 있으므로 "미등록"을 곧바로 위조로 판단하지 않습니다.
5. OCR 정확도가 더 필요하면 tesseract 대신 사업자등록증 전용 모델이 있는 OCR(예: 네이버 CLOVA OCR 사업자등록증 특화 API)로 `services/ocr.ts`만 교체하면 됩니다. 파서·검증·매칭 계층은 그대로 재사용됩니다.

이 구조는 코드에 반영되어 있고 `NTS_API_KEY`를 설정한 상태에서 2~4번이 동작하는 것을 확인했습니다. 다만 **실제 사업자등록증 이미지로 OCR → 진위확인 일치(`valid: "01"`)까지 이어지는 경로는 실제 등록증을 확보하지 못해 검증하지 못했습니다.** 번호·개업일·대표자명이 정확히 읽히면 일치로 응답한다는 것은 API 명세와 상태조회 결과로 뒷받침되지만, 이 마지막 연결은 가정입니다.

### 3-4-2. 디자인: 코워크시티의 시각 언어를 그대로 잇기

기존 UI를 복제할 필요는 없지만, 새 기능이 사이트의 일부처럼 보여야 사용자가 낯설어하지 않습니다. 실제 사이트에서 확인한 값으로 디자인 토큰을 정했고, 장식(그라데이션 히어로, 이모지 아이콘, 애니메이션)보다 **사용자가 지금 해야 할 일이 바로 보이는 것**을 우선했습니다.

- 홈은 마케팅 문구 대신 두 진입 경로(조건 입력 / 등록증)와 진행 순서만 보여줍니다.
- 업종 단계에는 "온라인 쇼핑몰, 앱 개발, 디자인…"처럼 사용자가 실제로 쓰는 표현의 빠른 선택 칩을 두어 한 번 클릭으로 시작할 수 있게 했습니다.
- 2~4단계 상단에 지금까지 고른 조건을 항상 표시하고 "변경"으로 바로 되돌아갈 수 있게 해, 뒤로 가기를 반복하지 않게 했습니다.
- 결과 카드는 이름 · 가격 · 추천 이유에만 위계를 주고, 사업자 유형·건축물 용도 같은 부가 정보는 상세로 옮겼습니다.

| 본문·테두리·보조 배경 | #1a1a1a / #e6e6e6 / #f5f5f5 | 전역 토큰 `ink`, `line`, `surface` |

### 3-5. 보안과 개인정보: 사업자등록증은 개인정보 문서입니다

등록증에는 대표자 이름, 사업장 주소, 사업자등록번호가 있습니다. OCR 기능을 붙이면서 다음 원칙을 코드에 반영했습니다.

| 위험 | 대응 | 위치 |
|---|---|---|
| 이미지·추출 정보가 서버에 남음 | 메모리에서만 처리, 디스크·DB·로그에 저장하지 않음. 처리 직후 이미지 버퍼를 0으로 덮어씀. OCR 원문은 응답에 포함하지 않고 추천에 필요한 필드만 반환 | `routes/business-registration.ts`, `services/business-registration-service.ts` |
| 오류 로그에 개인정보 유출 | 에러 핸들러가 요청 본문을 남기지 않고 오류 종류·메시지만 기록 | `lib/http.ts` |
| Content-Type 위조로 비이미지 업로드 | 매직 바이트로 실제 형식(PNG/JPEG/WEBP) 판별, 선언 형식과 불일치 시 거부. PDF는 매직 바이트로 확인 후 첫 페이지만 이미지로 변환해 동일 검증을 거침 | `lib/image-validation.ts`, `lib/pdf-conversion.ts` |
| 디컴프레션 폭탄·CPU 고갈 | 디코딩 전에 헤더에서 픽셀 크기를 읽어 한 변 6000px·20MP 초과 차단, 파일 10MB 제한, 요청당 파일 1개 | `lib/image-validation.ts`, multer limits |
| OCR 남용(무차별 요청) | IP당 속도 제한(429, 기본 300회/분, `OCR_RATE_LIMIT`로 조정). 운영에서는 로그인 사용자 단위로 더 낮게 | express-rate-limit |
| 응답 캐시·프록시 저장 | `Cache-Control: no-store` | 라우트 미들웨어 |
| 기본 보안 헤더 | helmet (nosniff, frame 차단 등), `X-Powered-By` 제거, CORS는 프론트 origin만 허용, JSON 본문 16KB 제한 | `index.ts` |
| 프론트에서 개인정보 잔류 | 추출 결과는 React 상태에만 두고 URL·localStorage에 넣지 않음. 추천 페이지로 넘길 때는 사업자 유형·지역·업종 id만 전달. 미리보기 blob URL은 화면을 떠날 때 해제 | `RegistrationResult.tsx`, `RegistrationUpload.tsx` |

**운영 환경에서 추가로 필요한 것**(이 과제 범위 밖이라 구현하지 않음): HTTPS 강제, 프록시 뒤에서의 `trust proxy` 설정(속도 제한이 실제 IP를 보도록), 인증된 사용자만 OCR 사용, 개인정보 처리방침에 OCR 처리 목적·보관 없음 명시. 또 tesseract.js는 브라우저에서도 동작하므로, 이미지가 아예 서버로 전송되지 않는 클라이언트 OCR로 전환하는 선택지도 있습니다.

### 3-6. 구조

```text
Next.js (App Router)  ──fetch──▶  Express API                      ──Prisma──▶  PostgreSQL
 /offices/recommend               /api/offices/recommend                        Industry, Office,
 /offices/recommend/registration  /api/industries/search                        OfficeIndustry (N:M),
 /offices/[id]                    /api/offices/regions, /api/offices/:id        OfficeBusinessType
                                  /api/business-registration/analyze ──tesseract.js──▶ 파싱 → 업종 매칭(DB)
```

- **업종 : 지점 = N : M** 관계를 테이블로 두어 "이 지점에서 이 업종으로 등록 가능한가"를 DB에서 바로 조회합니다. 실제 사이트의 지점 상세가 "계약 불가 업종"을 예외로 표시하는 것을 참고해, seed에서 예외 목록을 N:M 관계로 변환합니다.
- 필수 조건은 DB `where` 절에서 거르고, 점수 계산과 추천 이유 생성은 서버의 순수 함수(`backend/src/services/recommendation.ts`)로 분리해 단위 테스트가 가능하게 했습니다.
- 프론트는 지점 데이터를 갖고 있지 않고 API만 호출합니다. 로딩(스켈레톤), 오류(다시 시도), 빈 결과(완화 제안) 상태를 모두 구현했습니다.
- 입력한 조건과 현재 단계를 URL search params에 유지해, 지점 상세를 보고 돌아오거나 링크를 공유해도 같은 결과가 보입니다.

## 4. 검증 방법: 실제로 나아졌는지 어떻게 확인하는가

### 4-1. 지금 확인할 수 있는 것

**탐색 단계 비교** (현재 사이트 구조를 기준으로 한 추정)

| | 기존 흐름 | 개선 흐름 |
|---|---|---|
| 방문 페이지 | 업종 안내 → 지점 목록 → 지점 상세 (3종) | 추천 페이지 1개 (+ 상세) |
| 사용자가 해야 하는 판단 | 내 업종 찾기, 등록 가능 여부 확인, 필터 5종 조작, 상세에서 조건 재확인 | 사업 내용 검색, 선택 3번 |
| "왜 이 지점인가" | 사용자가 조건을 대조해 스스로 판단 | 카드에 추천 이유·미충족 조건 표시 |

**자동 테스트** (모두 통과)

| 종류 | 내용 |
|---|---|
| 백엔드 단위 테스트 45개 | 추천 (14) · OCR 파서: tesseract가 실제로 출력한 텍스트(표준 서식·정부24 사업자등록증명 표 서식 포함) + 오인식(라벨 공백, O/0, 글자 누락) + 실제 서식 라벨 + 비등록증 (11) · 업종 매칭 (6) · 이미지 검증 (6) · 국세청 진위확인: 키 없음/진위 일치·불일치/상태조회/미등록/오류·타임아웃 (8) |
| API 통합 테스트 34개 | 추천 시나리오, 업종 검색, 상세 (19) · 등록증 OCR(샘플 실제 인식, PDF 업로드, 잘못된 파일, 용량 초과) + 보안(Content-Type 위조, 디컴프레션 폭탄, no-store·보안 헤더, 속도 제한) (15) |

실행: `npm test`, `npm run test:api -w backend` (서버 실행 중일 때)

> 브라우저를 자동으로 조작하는 E2E(Playwright) 테스트는 만들지 않았습니다. 위 단위·통합 테스트가 API·로직 레벨의 검증이고, 화면 동작은 아래 QA 점검처럼 직접 눌러보며 확인했습니다.

**OCR이 실제로 동작하는지의 확인**: 샘플과 별개로, 무작위 사업자등록번호·상호로 새 등록증 이미지를 만들어 API에 넣었을 때 번호(검증 자리 포함)·상호·유형·업종 후보가 정확히 나왔습니다. 결과를 어디서 찾아오는 것이 아니라 tesseract가 이미지를 읽습니다.

**OCR 정확도의 근거와 한계**: 실제 사업자등록증은 개인정보가 있어 레포에 넣을 수 없으므로, 표준 서식을 따라 가상 정보로 생성한 이미지 3장(선명한 스캔본 2장, 기울기·그림자·노이즈를 넣은 촬영본 1장)으로 검증했습니다. 세 장 모두 인식 신뢰도 89~92%, 핵심 필드 전부 정확했습니다. 실제 촬영본(심한 기울기, 접힘, 저해상도)에서는 정확도가 떨어질 수 있어 확인·수정 화면을 필수로 두었습니다.

**QA 점검** (390 / 768 / 1024 / 1440px 화면 크기에서 주요 화면을 직접 눌러보며 확인. 자동화 도구는 쓰지 않았습니다)

- 확인 항목: 콘솔 오류, 가로 오버플로, alt 없는 이미지, 이름 없는 버튼, 지나치게 작은 터치 타깃, 히어로 장식과 제목 겹침, 기본 404 화면 노출
- 발견·수정: Next 기본 영문 404 → 사이트 톤의 404·오류 화면 추가 / "변경"·"조건 다시 설정하기"·푸터 링크 등 작은 터치 타깃 확대 / "~합니다"와 "~해요"가 섞인 문장 톤을 해요체로 통일 / 기본 파비콘 교체 / 첫 OCR 요청의 워커 초기화 지연을 서버 시작 시 미리 처리 / 업종 기본 목록을 가나다순 대신 등록 사례가 많은 업종 우선으로 / 결과 카드의 미충족 조건 중복 표시 제거

### 4-2. 실서비스에 적용한다면 측정할 지표

- 추천 결과에서 **상세보기 클릭률**, 이후 **문의/계약 전환율** (기존 지점 목록 경로와 비교)
- 추천 결과 **0건 비율**과 완화 제안 클릭률 (조건 설계가 너무 좁은지 확인)
- 업종 검색어 중 **결과 없음 비율** (키워드 보강 우선순위)
- 처음 방문 후 지점 상세 도달까지 걸린 시간 / 페이지 이동 수

## 6. 한계와 다음 단계

- 실제 지점·업종 데이터로 교체하려면 `backend/prisma/seed.ts`의 원본 데이터만 바꾸면 되고 API와 화면은 그대로 동작합니다.
- 업종 검색은 현재 `ILIKE` 부분 일치라 데이터가 커지면 `pg_trgm` 인덱스나 동의어 사전이 필요합니다.
- 지역 목록은 사이트에서 확인한 지역 중 일부와 과제 예시를 합쳐 구성했습니다. 실제 서비스의 지역 체계(창원, 충북, 경남 등)에 맞추면 됩니다.
- 기존 지점 목록 페이지를 대체하는 것이 아니라 **진입 경로를 하나 더 두는 것**을 의도했습니다. 조건을 이미 아는 사용자는 기존 필터가 더 빠를 수 있습니다.
- OCR은 이미지 전처리(기울기 보정, 이진화) 없이 tesseract.js를 그대로 사용합니다. 실제 촬영본 정확도를 올리려면 전처리와, 필요 시 사업자등록증 전용 OCR API(예: 네이버 CLOVA OCR)로 교체할 수 있도록 `services/ocr.ts` 한 곳에 엔진을 격리해 두었습니다.
- OCR 처리는 서버에서 하고 이미지를 저장하지 않지만, 실서비스라면 브라우저 안에서 OCR을 돌려(tesseract.js는 브라우저에서도 동작) 이미지가 서버로 전송되지 않게 하는 선택지도 있습니다.
